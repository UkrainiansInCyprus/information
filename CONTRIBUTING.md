# Contributing to the repository
## Overview
You have a few ways of contributing to the repository:
- Participating in the [Discussions](https://github.com/UkrainiansInCyprus/information/discussions);
- Participating in the [Wiki](https://github.com/UkrainiansInCyprus/information/wiki);
- Updating the source code:
    - By making a change request in an [Issue](https://github.com/UkrainiansInCyprus/information/issues);
    - By proposing a change in a [Pull Request](https://github.com/UkrainiansInCyprus/information/pulls);
- Contacting the maintainers directly via available channels (e.g. email, social media, etc).

## Contributing in the Discussions
In the discussion section you can ask questions, provide answers, and share your experience with the community. You can also propose new topics for discussion.
When doing so - please be respectful and follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Contributing in the Wiki
The wiki section is a place where you can share your knowledge and experience with the community. You can create new pages, edit existing ones, and add references to external sources. When doing so - please be respectful and follow the [Code of Conduct](CODE_OF_CONDUCT.md).

> [!IMPORTANT]
> Wiki is NOT meant to be used as a place to store the information regarding Cyprus or the Ukrainian community in Cyprus. Instead, it contains the information about the repository itself, its structure, and how to contribute to it (as well as build, share, etc). The information regarding Cyprus and the Ukrainian community in Cyprus is stored in the main repository AND/OR in the [Discussions](https://github.com/UkrainiansInCyprus/information/discussions).

## Contributing to the source code
As made clear in the overview section, there are two way to contribute to the source code. Let's go through them one by one.

### Making a change request in an Issue
If you want to propose a change to the source code, you can do so by creating an issue, if you're unsure of how/where to make the change, or how to word it properly.
There - follow the issue template and provide as much information as possible. The maintainers will review your request and provide feedback, after that - changes to the source code may be implemented by maintainers, or contributors to the repository, depending on the nature of the change and the availability of contributors.

You might be asked for more details, so please be responsive to the maintainers' requests. If you don't respond within a reasonable time frame, your issue may be closed.
You can reopen the issue, if you feel like you have more information to provide, or if you feel like the issue was closed prematurely.

When making requests for changes to the source code, please be respectful and follow the [Code of Conduct](CODE_OF_CONDUCT.md).

### Proposing a change in a Pull Request
If you want to propose a change to the source code, you can do so by [creating a pull request](https://docs.github.com/en/pull-requests/how-tos/create-pull-requests/creating-a-pull-request).
For that you'll need to fork the repository (unless you're a maintainer with write access, then you can create a new branch in the main repository), make your changes, and then create a pull request.

When creating a pull request, provide a helpful description of changes in the description field of the Pull Request, or by adding Review Comments to the code itself (note: not the comments IN the code, but TO the code on GitHub).
When updating the code - try to follow the existing code style, provide tests (if necessary for the changes made), and make sure that the code is working as expected, builds, doesn't disturb the existing functionality and data unless intended to do so, and doesn't introduce any security vulnerabilities.
You should also make sure that the code itself doesn't contain offensive or inappropriate content, and that it doesn't contain any personal information of any kind (e.g. email addresses, phone numbers, etc), unless explicitly allowed/when providing publicly available information.

For example, things such as variable names, function names, comments (that are not visible in the build output) should not contain any offensive or inappropriate content, discriminatory language, etc.

We ask you to be humble and respectful to the maintainers and other contributors, be open to the feedback, suggestions, and be willing to make changes to your code if requested by the maintainers (feel free to discuss/ask for clarifications). Being uncooperative, disrespectful, or unwilling to make changes to your code may result in your changes being rejected.

Contributors that are attempting to add malicious code, or destructive changes (such as removing the entire codebase, trying to delete the repository, etc) will be blocked from contributing to the repository and reported to GitHub.

When proposing changes to the source code, please be respectful and follow the [Code of Conduct](CODE_OF_CONDUCT.md).

## Contacting the maintainers directly
If you don't feel comfortable contributing to the repository in any of the ways mentioned above, you can contact the maintainers directly via available channels (e.g. email, social media, etc).
When doing so - please be respectful and follow the [Code of Conduct](CODE_OF_CONDUCT.md).

This option is also applicable in cases when a contributor doesn't want to create an account on GitHub, the best way to contribute to the repository, in this case would be to contact the maintainers, and provide with similar information to what would've been provided in a comment, an issue or a pull request.

> [!NOTE]
> For example, if unable to make a pull request, you can send a .diff file with `git diff` command output, or a .patch file with `git format-patch` command output, and the maintainers will apply the changes to the repository.
> The procedures for getting more information from the contributor still apply, but in a different contact environment (e.g. email, social media, etc).

Since this is a rather uncommon way of contributing, please be patient and understanding if the maintainers don't respond immediately, or if they ask for more information, or if they ask you to provide the information in a different way (e.g. via an issue or a pull request).
